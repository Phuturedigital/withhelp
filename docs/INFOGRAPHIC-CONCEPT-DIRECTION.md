# WITH. Infographic and Concept Demonstration Direction

## Purpose

WITH. is currently selling and validating an idea, not presenting a live national safety network.

The website therefore needs to help people **see the future system without mistaking a concept for live coverage**.

The role of diagrams and infographics is to make the idea understandable, credible and easy to imagine.

The creative rule is simple:

> Show how WITH. could work without pretending that it already does.

Every visual should do at least one of three jobs:

1. Help people understand the problem.
2. Help people imagine the future system.
3. Help a potential partner understand where they could fit.

The website is not a live operations dashboard at this stage.

---

## Core framing

The visual language must clearly separate **concept demonstration** from **live infrastructure**.

Use labels such as:

- Concept illustration
- Illustrative example
- Pilot scenario
- Proposed network model
- Example protection flow
- How WITH. could work
- Simulated coverage example

Avoid labels such as:

- Live coverage
- Active now
- Available here
- Current safe points
- Real time response coverage
- Safe area
- Protected zone

until those claims are genuinely true and operationally verified.

Recommended standard disclaimer for concept maps and network simulations:

> **Illustrative network example.** This visual demonstrates how Assistance Points, protected journeys and response connections could work. It does not represent live WITH. coverage or currently verified Assistance Points.

Recommended standard disclaimer for network growth visuals:

> **Concept model.** This illustration explains how the network could become more useful as people, businesses and organisations participate. It is not a forecast or live coverage measurement.

# The first five core visual stories

These five visuals should become the foundation of the website's visual storytelling.

## 1. Illustrative Coverage Map

### Purpose

Help people immediately understand what a WITH. network could physically look like in one neighbourhood.

### Working headline

> **What could a WITH. network look like around you?**

Alternative:

> **Imagine a neighbourhood where help is easier to reach.**

### Story

Use a clearly illustrative Johannesburg style neighbourhood or corridor.

The map can show examples such as:

- a pharmacy
- petrol station
- hotel
- mall security desk
- university or campus point
- staffed property reception
- professional response connection
- one protected user journey

The route should show how a user might move through the area and how different Assistance Points could become reachable options if something changes.

### What to show

- an example protected route
- 6 to 10 proposed Assistance Points
- different Assistance Point categories
- a temporary vulnerable moment
- a nearby option for help
- a responder or Trusted Circle connection represented abstractly
- optional soft coverage zones or walking distance rings

### What not to show

- exact real victim locations
- actual crime pins
- fake live responder vehicles
- fake current coverage numbers
- a green area labelled safe
- a red area labelled dangerous
- real businesses presented as partners unless they actually are

### Visual treatment

Use the WITH. palette:

- warm cream base
- near black map labels
- lime for protected or ready states
- coral for attention points
- muted neutral map roads

Coverage should look soft and illustrative, not military or surveillance based.

### Preferred interaction

Allow the user to toggle:

- Assistance Points
- Protected journey
- Trusted Circle
- Response path

The map should educate rather than behave like a real navigation product.

---

## 2. How WITH. Coverage Could Grow

### Purpose

Explain the network effect without implying that more app installs automatically guarantee safety.

### Working headline

> **The network becomes more useful as more people and places participate.**

Alternative:

> **Coverage grows when the network grows.**

### Core visual story

#### Stage 1: One person installs WITH.

They can already use:

- Guardian
- Safety Countdown
- Trusted Circle
- SOS
- Private Risk preparation

The product must be useful before network effects exist.

#### Stage 2: More people participate

The system gains more protected journey activity and stronger understanding of where people need support.

Only privacy safe and governed signals should be used.

#### Stage 3: Businesses participate

Potential Assistance Points begin to form around places people already use.

Examples:

- pharmacies
- petrol stations
- hotels
- campuses
- malls
- property receptions

#### Stage 4: Organisations participate

Employers, universities, banks, insurers, property groups and response providers can sponsor, connect or strengthen the network.

#### Stage 5: The network becomes more connected

Potential outcomes:

- more places that know how to help
- more sponsored access
- stronger response handoffs
- better route and coverage intelligence
- greater continuity when one layer fails

### Important language rule

Do not say:

> More users make you safer.

Prefer:

> More participation can make the network more useful and improve access to support.

---

## 3. One Install Matters

### Purpose

Answer the question:

> Why should I install this if the network is still new?

### Working headline

> **WITH. should be useful from the first install.**

### Visual flow

```text
One person installs WITH.
        ↓
They can protect their own journeys
        ↓
They add a Trusted Circle
        ↓
They can use Countdown, Guardian and SOS
        ↓
Their participation creates demand for better local support
        ↓
Businesses and organisations can join the network
        ↓
The area can become more connected over time
```

### Core message

Network effects should improve WITH., but they must not be required for basic usefulness.

The first user still gets value.

The tenth user improves local participation signals.

The hundredth user may make the case for stronger organisational participation.

The product must never become a system where safety only works once enough people have joined.

---

## 4. Protection Before, During and After

### Purpose

Show that WITH. is a continuous safety system rather than an emergency button.

### Working headline

> **Safety is bigger than the moment something goes wrong.**

### Before

Show:

- protection readiness
- Trusted Circle
- planned journey
- Safety Countdown
- Private Risk preparation
- nearby Assistance Point concepts
- device and connection readiness

Message:

> **Prepare before you need help.**

### During

Show:

- Guardian active
- meaningful route change
- discreet check in
- SOS
- Assistance Point route
- incident creation
- Trusted Circle and response in parallel

Message:

> **Keep the safety chain connected when something changes.**

### After

Show:

- verified safe arrival
- responder handover
- medical support
- trauma support
- legal or reporting pathways
- evidence and incident timeline
- ongoing safety planning

Message:

> **Safety does not end when the incident does.**

---

## 5. One Failure Should Not End the Chain

### Purpose

Make WITH.'s resilience principle visually understandable.

### Working headline

> **If one layer fails, the safety chain should keep going.**

### Example failure scenarios

#### Phone taken

Show:

- last trusted heartbeat remains server side
- incident stays open
- Trusted Circle can still be informed
- response process can continue from last known state

#### Mobile data disappears

Show:

- local protection continues
- events queue locally
- last server state is preserved
- fallback channels can be attempted

#### Trusted contact is unavailable

Show:

- more than one Trusted Circle member
- professional response path does not depend on one family member

#### One responder is unavailable

Show:

- escalation or alternative response path
- system does not treat "alert sent" as a completed response

#### User cannot press SOS

Show:

- active Guardian or Countdown can notice broken expectations
- discreet verification can occur
- missed confirmation can enter escalation logic

### Visual structure

The visual should resemble a network with several paths rather than a single linear chain.

Avoid making this look like a technical cloud architecture diagram on the consumer website.

The technical version can live in documentation.

# Assistance Point concept visual

This deserves its own major illustration because the idea is unfamiliar.

## Headline

> **A place that knows how to help.**

## Supporting copy

> WITH. is exploring how ordinary staffed places such as pharmacies, petrol stations, hotels, campuses and retail locations could become verified Assistance Points with a clear procedure for helping someone who needs support.

## Visual sequence

1. A person enters or arrives at an Assistance Point.
2. The place acknowledges the request.
3. The person is moved to a visible staffed waiting area.
4. The business does not confront the suspected threat.
5. The WITH. incident remains connected to the wider safety network.
6. Trusted Circle or professional response can continue the handoff.
7. The event is resolved only by the appropriate user or authorised response layer.

## Important distinction

Do not visually imply:

> This shop is safe.

Communicate:

> This place has a verified process for helping.

The visual symbol should therefore communicate **assistance** rather than a shield claiming guaranteed safety.

# Visual design language

Infographics must feel like the WITH. product rather than generic corporate diagrams.

## Principles

### Human before technical

People should understand the situation before seeing system components.

### Low information density

One visual should teach one idea.

### Progressive disclosure

Start simple, then allow interaction or scrolling to reveal more detail.

### Calm composition

Use whitespace, rounded geometry and restrained labels.

### No fear theatre

Avoid:

- red flashing crime markers
- weapons
- dark alley imagery
- attack reenactments
- silhouettes following women
- "danger zone" maps

### No fake precision

Avoid exact looking data if it is simulated.

Do not display:

- 92% safer
- 3.2 minute response time
- 84% coverage
- exact Assistance Point count

unless supported by actual measured data.

### Concept data should look conceptual

Use wording such as:

- Example
- Proposed
- Illustrative
- Simulated
- Pilot model

within the visual itself, not only in a hidden footer.

# Visual brand states

## Cream

Normal life, context, background and everyday state.

## Lime

Ready, protected, acknowledged, verified process, connected state.

Lime does not mean guaranteed safe.

## Coral

Attention, change, incident activation and calls to action.

Coral should not turn the site into an alarm interface.

## Near black

System, trust, serious information and resilience.

## Grey and neutral tones

Roads, secondary systems, inactive network components and context.

---

# Diagram style rules

## Nodes

Rounded, simple, labelled with plain language.

Prefer:

> Trusted Circle

instead of:

> Contact notification subsystem

Prefer:

> Nearby help

instead of:

> Assistance Point discovery layer

## Lines

Lines communicate relationships and handoffs.

Use solid lines for the main user journey.

Use softer secondary lines for fallback paths.

Use coral only where attention or escalation occurs.

Use lime for confirmed or protected paths.

## Arrows

Do not overload diagrams with arrows.

A diagram should still make sense at mobile width.

## Icons

Use familiar simple icons for:

- person
- phone
- watch
- home
- business
- responder
- route
- circle / trusted people
- assistance

Avoid tactical, military and policing iconography as the default brand language.

# Technology direction for the visuals

The technology should serve the story rather than determine it.

## Concept maps

Preferred direction:

**MapLibre GL JS** for interactive concept maps once the website moves beyond static mockups.

Use it initially for illustrative network layers rather than live Assistance Point data.

## Coverage geometry

Use **Turf.js** if the concept map needs walking distance buffers, illustrative radiuses, corridor calculations or future geospatial analysis.

## Infographic charts

Use **Apache ECharts** when the visual is chart driven, for example:

- network growth stages
- pilot participation
- Assistance Point distribution once real data exists
- response funnel once operational data exists

## System diagrams

Use **Mermaid** for diagrams that must remain easy to maintain in documentation.

Use **React Flow / XYFlow** when a premium interactive system map is valuable on the public website.

## Important implementation rule

Do not add a visualisation library simply because it can make a chart.

A custom HTML, SVG or CSS visual is preferable when the story is simple.

The website should remain fast and understandable.

# Selling the idea without overselling it

The website must balance ambition and honesty.

It should make people think:

> I understand what this could become.

not:

> They are pretending this already exists.

The creative system should therefore show **possibility with clear boundaries**.

The strongest demonstrations are not fake dashboards.

They are simple stories showing:

- what changes for one person
- how one business can participate
- how one organisation can sponsor access
- how one protected journey works
- how multiple parts form a network

---

# Transition from concept to live product

The visual system should be designed so it can mature without being replaced.

## Research stage

Use:

- illustrative map
- hypothetical scenarios
- proposed Assistance Points
- simulated coverage

## Pilot stage

Introduce real pilot data with clear scope:

- pilot corridor
- participating Assistance Points
- invited user count
- verified operational status
- measured acknowledgement time

Label pilot information explicitly.

## Operational stage

Only once infrastructure is genuinely live can the site display:

- actual Assistance Point status
- real coverage boundaries where meaningful
- real service availability
- measured response metrics

Concept visuals should then remain available as educational explanations, while operational data becomes a separate live product surface.

---

# Creative approval checklist

Before publishing any infographic, ask:

1. Is it obvious whether this is real or illustrative?
2. Does the visual teach one clear idea?
3. Does it preserve the dignity and privacy of the people represented?
4. Does it avoid fear based imagery?
5. Does lime mean ready or connected rather than guaranteed safe?
6. Does the visual avoid fake precision?
7. Does it explain WITH. rather than simply decorate the page?
8. Can it be understood on a phone?
9. Does it reinforce continuity rather than only emergency response?
10. Would a reasonable viewer mistakenly believe coverage already exists?

If the answer to question 10 is yes, the visual needs to be redesigned or labelled more clearly.
